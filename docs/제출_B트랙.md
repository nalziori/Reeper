# Reeper 제출 자료 초안 — B 트랙(에이전트)

2026-11-19 기준, `main` `d5e89e9` 위의 `66c9967`. 소개서와 AI 활용 내역에 넣을 B 트랙 몫만 적었다. 이 파일이 원본이고 `제출_B트랙.docx`는 여기서 내보낸 것이다.

숫자의 출처는 `eval/README.md`의 실행 기록과 `docs/평가_결과.md`다. 예외는 둘이다. 누적 API 비용은 키 주인이 OpenAI 대시보드에서 읽은 값이라 저장소로 확인할 수 없다. 배포에서 잰 호출 수는 화면을 한 번 눌러 본 기록이고 채점한 평가가 아니다(`docs/배포.md`).

## 1. 맡은 범위

B 트랙은 Reeper에서 LLM이 닿는 부분 전부를 맡았다. 파일로는 `backend/app/agent.py`와 그 테스트다.

| 기능 | LLM이 하는 일 | 결과가 쓰이는 곳 |
|---|---|---|
| 답장 읽기 | 업체 답장을 여덟 유형 중 하나로 분류하고 제시 금액을 뽑는다 | 사용자가 "맞아요"로 확정해야 사건에 기록된다 |
| 답장 분석 | 답장의 주장을 문장 단위로 짚고 근거 표의 항목에 연결한다 | 사용자에게만 보이는 참고 글 |
| 전략 요약 | 사용자가 적은 상황으로 쓸 근거, 다툼이 될 특약, 예상 반론, 주의점, 되물을 것을 정리한다 | 사용자에게만 보이는 참고 글 |
| 말투 다듬기 | 고정 문안의 어미만 정중하게 또는 단호하게 바꾼다 | 검사를 통과한 경우에만 업체에 보낼 문안으로 쓴다 |
| 계약서 사진 읽기 | 사진에서 아홉 가지 값을 읽고 확신도와 읽은 자리를 돌려준다 | 입력 칸을 채우고 사용자가 확인한다. 기본은 꺼짐이고 Render 배포에서도 꺼 두었다 |

## 2. 설계 원칙: LLM에게 맡기지 않은 것

- **금액은 LLM이 만들지 않는다.** 환불액은 규칙 코드(`rules.py`)만 계산한다. LLM이 쓴 글에 서버 계산값이 아닌 금액이 있으면 그 항목을 버린다.
- **사건 단계는 LLM이 바꾸지 않는다.** 답장을 읽은 결과는 제안일 뿐이고, 사용자가 확정해야 단계가 넘어간다.
- **업체에 보내는 글은 고정 양식이다.** 초기 실험에서 LLM이 직접 쓴 통지문은 고정 양식보다 길고 어색했고 프롬프트 말투가 샜다. 그래서 LLM은 사용자에게 보여 줄 분석만 쓰고, 보내는 글은 말투만 다듬게 했다.
- **근거는 확인된 표 안에서만 고른다.** 법령 이름이나 조문을 글로 쓰지 못하게 하고 근거 표의 id로만 가리키게 했다. 표에 없는 근거가 나오면 버린다.
- **LLM이 없어도 끝까지 간다.** 호출이 실패하거나 하루 상한(Render 배포 100회)을 넘으면 키워드 판정과 고정 양식으로 접수부터 종결까지 진행된다. 이 경로는 키 없는 테스트로 고정했다.
- **에이전트는 보내지 않는다.** 문자를 보내고 전화하는 것은 사용자다. 통화를 듣는 기능도 없다.

| 법령 | 법령 이름, 조문 번호, 판결, 시행령, 표준약관 같은 표 밖 인용 |
| 표현 | 무효, 위법, 불법, 소송, 고소, 고발, 손해배상, 형사, 처벌 같은 압박 표현 |
| 비율·연락처·날짜 | 자료에 없는 퍼센트, 전화번호와 주소(1372 제외), 사건에 없는 날짜 |
| 인용 | 답장 원문에 없는 문장을 인용이라고 내놓는 것 |
| 말투 다듬기 | 문장 수와 길이가 달라진 글, 해지·오늘·개인 사정 같은 핵심 낱말이 빠지거나 바뀐 글, 상호가 바뀐 글, "요청"이 "문의"로 약해진 글 |

### 틀릴 때 얼마나 위험하게 틀리는가

답장 읽기는 정답률만 보면 안 된다. 오류마다 결과가 다르다. `eval/run.py`가 틀린 건을 세 등급으로 센다(`docs/어려운_답장_작업_분담.md` C1).

- 위험: 수용이 아닌데 수용으로 읽음(바로 합의가 된다), 없는 금액을 읽음, 금액을 틀리게 읽음
- 중간: 유형끼리 헷갈림, 제시액을 못 읽음(사용자가 금액을 넣는다)
- 안전: "잘 모르겠어요"로 읽음(사용자가 버튼으로 고른다)

| 판정 | 자료 | 유형 정답률 | 위험 오류율(95% 구간) | 오답 중 "잘 모르겠어요" |
|---|---|---|---|---|
| 실제 모델 | 164건(답장 64 + 어려운 100) | 162/164, 98.8%(95.7~99.7%) | 0/164, 0.0%(0.0~2.3%) | 2/2 |
| 키워드 판정 | 같은 164건 | 77/164, 47.0%(39.5~54.6%) | 0/164, 0.0%(0.0~2.3%) | 84/87, 96.6% |
| 실제 모델 | 변형 435건 | 435/435, 100%(99.1~100%) | 0/435, 0.0%(0.0~0.9%) | 오답 없음 |
| 키워드 판정 | 변형 435건 | 244/435, 56.1%(51.4~60.7%) | 0/435, 0.0%(0.0~0.9%) | 187/191, 97.9% |
| 실제 모델 | 사람이 쓴 어려운 20건 | 17/20, 85.0%(64.0~94.8%) | **1/20, 5.0%(0.9~23.6%)** | 2/3 |
| 키워드 판정 | 사람이 쓴 어려운 20건 | 11/20, 55.0%(34.2~74.2%) | 0/20, 0.0%(0.0~16.1%) | 8/9 |

- 구간은 Wilson 95% 구간이다. 위험 오류가 0건이어도 164건으로는 "2.3% 아래"까지만 말할 수 있다.
- 실제 모델의 164건 줄은 새로 돌린 것이 아니다. 기록된 두 실행(답장 64건 반복 실행, 어려운 답장 100건)의 오답 2건에 같은 등급 규칙을 적용했다. 두 건 모두 "잘 모르겠어요"로 읽었다.
- 키워드 판정은 정답률이 낮지만 틀릴 때 거의 "잘 모르겠어요"로 틀린다. LLM이 죽어도 잘못된 합의나 없는 금액이 생기지 않게 하는 것이 목표였다. 다만 규칙을 이 164건을 보며 고쳤으므로 164건의 0건은 처음 보는 답장의 숫자가 아니다.
- 변형 435건은 답장 64건에 띄어쓰기·맞춤법·반말·금액 표기 같은 변형을 규칙으로 입힌 것이다(C 트랙, `eval/perturb.py`). 키워드 판정은 처음에 여기서 위험 1건이 나왔다. "47만 3,334원"을 3,334원으로 읽었다. 고친 뒤 0건이고, 같은 일이 다시 생기면 테스트가 실패하게 평가 답장과 변형을 회귀 테스트로 고정했다(지금 619건: 164 + 사람이 쓴 20 + 변형 435).
- 실제 모델은 변형 435건을 모두 맞혔다(한 번 실행, 제시액 144/144). 띄어쓰기·맞춤법·반말·금액 표기가 달라져도 읽기가 흔들리지 않는다는 뜻이다. 변형의 원본 64건은 모델이 이미 다 맞히던 답장이고 그중 30건은 프롬프트를 고칠 때 본 것이라, 처음 보는 어려운 답장의 점수는 아니다. 그 점수는 어려운 답장 100건의 98/100이다.
- **실제 모델의 위험한 오답은 사람이 쓴 20건에서 처음 나왔다.** "…꼭 환불해드릴테니 기다려주세요. … 근데 이번 달 안에는 환불이 어렵습니다"를 수용으로 읽었다(정답은 미루는 답). 환불하겠다는 말과 미루는 말이 한 답장에 같이 있는 경우다. 앞의 599건에서 0건이던 것은 그 자료에 이런 문장이 없었기 때문이지, 모델이 이런 답장을 안전하게 읽는다는 뜻이 아니었다. 20건이라 구간이 넓다(0.9~23.6%). 고치지 않았다. 이 20건을 보고 프롬프트를 맞추면 이 자료도 튜닝 후 점수가 된다.
- 이 오답이 바로 합의로 이어지지는 않는다. 화면은 읽은 결과를 보여 주고 "기록하면 …원으로 합의하고 입금 기한을 잡아요"라고 알린 뒤 사용자가 "맞아요"를 눌러야 기록한다. 마지막 방어는 사람의 확인이다.
- 나머지 두 건("하루에 8000원인데 제해서 환불하겠습니다", "네 ㄴㄴ")은 "잘 모르겠어요"로 읽었다. 쓴 사람별로는 사람 7/8, Claude 7/7, 사람 문장을 바꾼 것 3/5다.
- 키워드 판정은 이 20건에서 처음에 위험 1건이 나왔다. "하루 8000원이니 다시 계산해서 보내드릴게"의 하루 단가를 제시액으로 읽었다. 단가는 제시액으로 읽지 않게 고쳐 0건이다. 고친 뒤 숫자이므로 이것도 튜닝 후 점수다.
- 화면에서도 한 번 더 막는다. 키워드로 읽은 수용과 금액은 확정 버튼이 없고 사용자가 직접 고른다.

첫 사진 실행에서 가장 위험했던 오류는 보증금이 합쳐 적힌 계약서에서 결제 금액을 650,000원으로 읽고 확신도 1.00을 준 것이다. 정답은 600,000원이다. 확인 표시도 붙지 않는 오류라, 프롬프트에 "보증금을 뺀 금액이 적힌 자리를 읽고 계산하지 않는다"를 넣어 고쳤다.

## 5. 일반 LLM에 그냥 물었을 때와의 차이

같은 상황 10건을 아무 장치 없이 같은 모델에 물어 비교했다.

- **금액 계산은 일반 LLM도 잘했다.** 10건 중 6건이 정확히 같았고, 소비자 사정으로 해지하는 7건은 모두 1원 안쪽이었다. Reeper의 차별점은 계산 정확도가 아니다.
- **차이는 하지 말아야 할 것에서 났다.** 사용자가 소송 예고와 전액 환불을 넣어 달라고 하자 일반 LLM은 그대로 써 주었다. 근거 표에 없는 기준을 6건에서 인용했고, 확인되지 않은 수치를 단정했다.
- Reeper는 같은 요구에 "전액은 어렵다"고 알려 주고, 확인된 근거만 쓰고, 업체 사정이 보이면 위약금을 단정하지 않고 되묻는다.

| 허점 점검 | Claude Code | 나쁜 출력을 끼워 검사의 구멍 찾기 | 고칠 범위 결정 |
| 배포 확인 | Claude Code + 브라우저 자동화 | Render 배포에서 접수부터 종결까지 눌러 보기(`docs/배포.md`) | API 키 입력, 배포 설정 |

사람이 쥐고 있던 것은 네 가지다. 유료 API 호출 승인, PR 승인과 병합, API 키 입력, 그리고 "보내는 글은 고정 양식으로 둔다" 같은 방향 결정이다.

AI와 일하면서 정한 규칙도 있다. 모든 평가 수치에 실행한 커밋과 한계를 같이 적었다. 같은 자료로 고치고 잰 점수는 "튜닝 후 점수"라고 표시하고 처음 보는 자료로 따로 쟀다. 데이터는 가상 계약서와 가상 답장만 썼다.

## 7. 비용과 운영

- 사건 하나를 끝까지 진행하면 실제 모델 호출은 7회 안팎, 약 1만 토큰, 약 0.02달러다(2026-11-17 Render 배포에서 한 번 눌러 본 값, 금액은 추정).
- 전략 1건이 약 3,300토큰으로 가장 크다. 답장 읽기는 약 500토큰이다.
- Render 배포는 하루 100회 상한을 두었고 사진 읽기는 꺼 두었다. 서버는 사건과 계약 내용을 저장하지 않는다.
- 공개 주소로 들어오면 키워드 판정으로 돌고, 심사용 비밀 주소(`/unlock/<값>`)로 들어온 브라우저만 12시간 동안 실제 모델을 쓴다(#103). 공개 저장소에 배포 주소가 알려져도 API 키가 쓰이지 않게 하려는 것이다. 값은 키 주인만 알고 저장소·PR에 적지 않는다.
- 개발과 평가에 쓴 누적 API 비용은 전체 기간 1.82달러다(2026-11-19, 키 주인이 대시보드에서 확인). 2026-11-18에는 1.27달러였다.

## 8. 알려진 한계

고칠 수 있는 것은 고쳤고, 아래는 이번 제출에서 고치지 않기로 한 것이다. 남은 일이 아니라 한계다.

**평가의 한계**

- 평가 자료가 작다(답장 184건과 변형 435건, 사진 27장, 상황 10건과 실제 사례를 본뜬 12건). 답장 64건 반복 실행 외에는 한 번씩만 돌렸다.
- 프롬프트를 쓴 쪽과 독립해서 쓴 것이 기록으로 확인되는 자료는 A가 직접 쓴 8건뿐이다(역할 카드 20건 중). 여기서 정답률이 85%로 내려가고 위험한 오답이 1건 나왔다. 다른 자료의 만점은 쉬운 자료이거나 프롬프트를 맞춘 자료라는 점을 같이 읽어야 한다.
- 어려운 100건의 문장과 정답은 모델이 초안을 썼고, 사람은 4건만 확인했다.
- 계약서 사진은 워드에서 내보낸 깨끗한 이미지로만 쟀다. 폰으로 찍은 사진은 재지 않았다. 배포에서는 사진 읽기를 꺼 두었다.

**고치지 않은 오답**

- 환불하겠다는 말과 미루는 말이 같이 있는 답장을 실제 모델이 수용으로 읽는다(사람이 쓴 20건의 1건). 사용자가 확정해야 기록되므로 화면에서 걸러진다.
- 어려운 100건에서 틀린 두 건("매월 1일에만 접수", "없는 번호")과 사람이 쓴 20건의 두 건은 "잘 모르겠어요"로 읽는다. 사용자가 버튼으로 고른다.
- 평가 자료를 보고 프롬프트를 맞추면 그 자료의 점수가 의미를 잃으므로, 이 오답들은 고치지 않고 기록했다.
- 개시 전 해지 상황에서 전략이 위약금을 단정한다. 개시 전 해지의 기준(소비자분쟁해결기준)을 이번에는 근거 표에 넣지 않기로 해서(C 트랙 결정) 고치지 않았다. 전략은 사용자에게만 보이는 참고 글이다.

**제품의 범위**

- 코드 검사는 숫자와 낱말을 본다. 숫자가 없는 해로운 조언이나 한글로 쓴 금액은 잡지 못한다.
- 키워드 판정은 한글로 쓴 금액("사십만 원")을 읽지 않고, 띄어쓰기를 없애거나 반말로 바꾼 답장 일부를 "잘 모르겠어요"로 읽는다. 위험하게 틀리지는 않아 규칙을 늘리지 않았다.
- 계산은 소비자 사정으로 해지하는 헬스·피트니스와 요가·필라테스 회원권만 다룬다. 업체 잘못이거나 다른 업종이면 1372 상담을 안내한다. 휴회 기간, 총액의 일부만 낸 계약, 업체 귀책 배상은 계산하지 않는다(실제 조정 사례를 본뜬 12건에서 확인).
- 전략은 받은 시점의 글이다. 통지 전에 받은 조언의 "아직 알리지 않았으므로…" 같은 문장은 통지 뒤에도 다시 받기 전까지 남는다.
- 새 화면(shadcn)의 실제 모델 경로는 로컬 서버에서 휴대폰 폭으로 한 번 끝까지 눌러 봤다(호출 8회, 오류 0). 배포 주소에서는 새 화면으로 다시 확인하지 않았다.
