# 개발 계획

작성일: 2026-11-14 / 개발 기간: 11/15~11/22 / 제출: 11/23 17:00 전

**상태: 초안이다.** 아래 기술·API·일정은 제안이며 구현 현황이 아니다. 제품 내용은 [기획안](기획안.md)을 따른다.

## 목표

심사위원이 링크 하나로 접속해 혼자 3분 안에 다음을 끝까지 본다.

샘플 계약서 선택 → 추출 결과와 환불액 → 해지 요청 문안 승인 → 심사위원이 사장 역할로 답하거나 무시 → 에이전트의 대응 또는 시간 경과 후 재요청·에스컬레이션 → 타임라인

## 범위

- **만든다**: 계약서 추출, 환불액 계산, 해지 요청 문안, 사장 역할 입력, 답장 분류와 다음 행동, 무응답 경로와 시간 건너뛰기, 내용증명·1372 신청서 초안, 타임라인, 평가 스크립트.
- **만들지 않는다**: 실제 문자·이메일 발송, 답장 자동 수신, 음성·통화, 로그인과 회원, 업체 폐업·연락 두절 사건, 소송 대응, 헬스장 외 업종.
- **대상 계약**: 기간제 회원권과 횟수제 PT의 사용자 사정 중도해지. 횟수제는 계산 규칙이 확인되면 넣고, 안 되면 기간제만 한다.

## 기술 (제안)

- 서버: Python, FastAPI, SQLite. 테이블은 사건(상태 JSON)과 사건 기록 2개.
- 화면: React + Vite, 모바일 폭 우선. 팀이 더 익숙한 것이 있으면 그것을 쓴다.
- LLM: 제공자 1개. 함수는 추출·분류·문안 3개이며 각각 가짜 구현을 둔다.
- 배포: HTTPS 링크 하나. 제출 요건을 확인한 뒤 환경을 정한다.

## 공유 계약 (초안)

- **사건 상태**: case_id, contract(결제액·기간·개시일·특약), refund(법정 환불액·계산 내역), target(목표 금액·최저 수용선), stage, notified_at(도달일), deadline_at, now(가상 시계).
- **사건 기록**: record_id, case_id, type(sent/received/time_passed/decision/approval), text, classification, created_at.
- **단계(stage)**: intake → calculated → notified → waiting → responding → escalated → settled.
- **API**:
  - `POST /cases`: 샘플 계약서로 사건을 만든다. 추출 결과와 환불액을 반환한다.
  - `GET /cases/{id}`: 사건 상태와 타임라인을 반환한다.
  - `POST /cases/{id}/approve`: 문안 발송이나 문서 제출을 승인한다.
  - `POST /cases/{id}/reply`: 업체 답장(버튼 또는 자유 입력)을 넣는다. 분류와 다음 행동을 반환한다.
  - `POST /cases/{id}/advance`: 가상 시계를 며칠 넘긴다. 기한이 지났으면 다음 행동을 반환한다.
- 단계 전이와 금액 비교는 서버 규칙이 한다. LLM은 상태를 직접 바꾸지 않는다.

- 리뷰: 1번 PR은 2번이, 2번 PR은 3번이, 3번 PR은 1번이 본다.

## 완료 기준

- 로그인과 마이크 없이, 데스크톱과 모바일 모두에서 3분 안에 종결까지 간다.
- LLM이 실패해도 준비된 문안과 버튼으로 끝까지 진행된다.
- 환불액은 가상 계약서 정답과 일치한다. 일치율을 기록한다.
- 답장 분류 정확도와 금액 추출 정확도를 기록한다. 목표 수치는 첫 측정 후 정한다.
- 표 밖의 법적 근거를 인용한 응답이 0건이다.
- 최저 수용선보다 적은 제시액에는 항상 경고가 뜬다.
- 화면과 소개서에 "오늘 실제로 되는 것"과 "시연용 모의"가 구분되어 있다.
- 일반 테스트는 가짜 LLM으로 키 없이 통과한다.

## 늦어질 때 줄이는 순서

1. 1372 신청서 초안을 뺀다. 내용증명까지만 한다.
2. 횟수제 PT를 빼고 기간제 회원권만 한다.
3. 계약서 사진 추출을 빼고 값 직접 입력으로 바꾼다. 샘플 계약서는 미리 추출해 둔다.

환불액 계산, 사장 역할 입력과 답장 분류, 무응답 경로와 시간 건너뛰기, 타임라인은 끝까지 유지한다.

## 작업 규칙

- 작업별 브랜치(`feature/`, `fix/`, `docs/`)에서 PR을 올리고 다른 담당자 1명이 본다.
- 공유 계약을 바꿀 때는 영향을 받는 담당자와 먼저 조율한다.
- 확인되지 않은 법령 내용이나 조문 번호를 만들어내지 않는다. [환불 규칙](환불_규칙.md)에 "확인 필요"로 남긴다.
- API 키와 개인정보를 저장소에 넣지 않는다. 계약서와 대화는 가상 샘플만 쓴다.
- 유료 서비스 도입, 예산 초과, 공개 범위 변경은 사람이 정한다.
