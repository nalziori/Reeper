# 브랜치 규칙

`main`은 항상 배포할 수 있는 상태로 둔다. 모든 변경은 짧은 브랜치와 PR로 들어온다.

## 이름

`<종류>/<짧은-설명>` 형식으로 쓴다. 설명은 영문 소문자와 하이픈만 쓰고 세 단어 안팎으로 줄인다.

| 종류 | 쓰는 때 | 예 |
|---|---|---|
| `feature` | 기능을 더하거나 바꾼다 | `feature/agent-openai` |
| `fix` | 버그를 고친다 | `fix/reply-amount` |
| `docs` | 문서만 바꾼다 | `docs/refund-rules-check` |
| `eval` | 평가셋, 평가 스크립트, 평가 결과 | `eval/replies-b` |
| `chore` | 설정, CI, 의존성 | `chore/ci-cache` |
| `spike` | 버릴 수도 있는 실험 | `spike/strategy` |

## 만들고 올리기

- 최신 `main`에서 만든다. 다른 사람의 브랜치 위에 쌓지 않는다.
- 브랜치 하나는 한 가지 일만 한다. 기능과 문서 정리를 섞지 않는다.
- `main`에 직접 푸시하지 않는다. PR을 열고 리뷰 1명의 승인을 받는다.
- 리뷰는 A의 PR을 B가, B의 PR을 C가, C의 PR을 A가 본다. `docs/계약.md`와 `backend/app/models.py`가 바뀌면 세 명이 모두 본다.
- CI(서버 테스트, 화면 빌드)가 통과해야 병합한다. 병합한 브랜치는 지운다.
- 하루 넘게 열어 두지 않는다. 길어지면 쪼개서 먼저 되는 부분을 올린다.

## 담당 밖 파일을 바꿀 때

- 먼저 담당자에게 맡길 수 있는지 본다. 꼭 필요한 변경만 한다.
- PR 본문 맨 위에 어떤 파일을 왜 바꿨는지 표로 적는다.
- 필요하지 않았던 변경은 올리기 전에 되돌린다.

## `main`과 어긋났을 때

- 자기 브랜치에 `main`을 병합하거나 리베이스해서 맞춘다.
- 다른 사람이 받아 간 브랜치에는 강제 푸시를 하지 않는다.

## 실험 브랜치

- `spike/`는 병합하지 않는다. 결과를 팀에 보여 주는 용도다.
- 쓰기로 정해지면 `feature/` 브랜치를 새로 만들어 테스트와 함께 다시 올린다.

## 커밋 메시지

`<종류>: <한 줄 요약>` 형식으로 쓴다. 종류는 `feat`, `fix`, `docs`, `test`, `chore`를 쓴다.
