# 평가 결과

3단계 통과 조건([개발 계획](개발_계획.md))에 필요한 문서다. 측정 방법과 원자료는 [eval/README.md](../eval/README.md)에 있고, 여기에는 보고할 숫자와 읽을 때 주의할 점만 모은다.

모델: `gpt-6.1-terra`. 실제 모델 실행은 모두 B가 했다. 사진 고치기 전 실행(3절)만 2026-11-15이고, 나머지는 2026-11-16이다. 모든 숫자는 한 번 실행한 결과다. 비용은 입력·출력을 나눠 재지 않은 추정이다.

## 한눈에

| 평가 | 결과 | 한계 |
|---|---|---|
| 답장 읽기 30건 | 유형 24/30 → 판정 기준 반영 후 30/30, 제시액 10/10 | 30/30은 같은 30건으로 튜닝한 뒤의 점수다. 각각 한 번 실행 |
| 전략 10건 | 필수 근거 11/11, 표 밖 근거 0, 금지 근거 위반 0, 업체 귀책 내용 검사 실패 0 | 금지 근거는 실행 뒤에 정하고 그 실행의 근거 id로 다시 셌다. 근거 id와 단어·구절 검사만 했다. 전략 문장은 출력되지 않아 검토하지 못했다 |
| 계약서 사진 12장 | 5개 필드 54/60 → 프롬프트 수정 후 60/60, 전부 맞은 사진 12/12 | 60/60은 같은 12장으로 튜닝한 뒤의 점수이고, 깨끗한 Word 이미지다. 각각 한 번 실행 |
| 계약서 사진 10장 (튜닝에 안 쓴 건) | 5개 필드 50/50 (B 실행, #49) | 같은 생성기의 깨끗한 쉬운 이미지다. 정상가 병기나 결제금액에 보증금이 합산된 건은 없다. `run.py`가 아닌 임시 스크립트로 채점했다 |
| 말투 다듬기 8건 | 8/8 검사 통과, 금액·날짜·조문·근거 그대로 | 정답과 비교한 점수가 아니다. 양식 4개 × 말투 2개만 돌렸다 |
| 환불액 계산 | 가상 계약서 22/22 정답 일치 | 해석을 확인하지 않은 `unverified_month` 5건은 뺐다(27건 전체도 기대값과 같다). 규칙 계산(`rules.py`)이라 LLM과 무관하다 |

## 1. 답장 읽기 (`eval/run.py --live`)

업체 답장 30건(`replies_b.jsonl` 12건, `replies_c.jsonl` 18건)을 읽어 유형과 제시액을 맞히는지 본다.

| 실행 | 커밋 | 유형 | 제시액 | 호출·토큰 | 비용 |
|---|---|---|---|---|---|
| 첫 실행 | `991fc8d` | 24/30 (80.0%) | 10/10 | 30회, 10,691 | 약 0.015달러 |
| 판정 기준 반영 후(#41) | `991fc8d` + 커밋 전 프롬프트 수정 (B 확인: 이 수정을 실행 29초 뒤 `422d271`로 커밋, 그 사이 추가 수정 없음) | 30/30 (100.0%) | 10/10 | 30회, 14,062 | 약 0.02달러 |
| 가짜 LLM 기준선(키워드) | `c1f4d62` | 33.3% | 50.0% | 0회 | 0 |

- 첫 실행에서 틀린 6건(c07, c11, c13, c15, c17, c18)은 모두 `unknown`으로 읽었다. 당시 프롬프트에 판정 기준(미루는 답은 `callback`, 다른 창구는 `visit`, 적립금·양도·신고 안내는 `refuse`)이 없었다. 이것이 원인일 수 있지만 한 번의 실행으로 확정할 수는 없다.
- **30/30은 튜닝 후 점수다.** 판정 기준은 c07, c11~c18에서 나왔고(`eval/README.md`), 이 범위에는 첫 실행에서 맞힌 c12, c14, c16도 들어 있다. 그 기준을 프롬프트에 넣었으므로 "정한 기준대로 읽는다"는 뜻이다. 처음 보는 답장에서의 성능 근거가 아니다. 보고할 때는 "24/30 → 30/30(같은 30건)"으로 함께 적는다.
- 제시액 정답률은 정답이 `low_offer`인 10건만 센다.

## 2. 전략 (`eval/run.py --plans --live`)

상황 설명과 계약 10건(`situations_b.jsonl`)으로 `agent.plan`을 부른다. 커밋 `991fc8d`, 10회, 32,199토큰.

- 필수 근거 11/11. 필수 근거가 비어 있는 s08은 재현율에서 뺐다. 이 숫자는 근거 id가 맞았다는 뜻이고 전략 문장 전체가 정확하다는 뜻이 아니다. 발표 자료에 옮길 때도 "근거 id 기준"이라고 함께 적는다.
- 표 밖 근거 0, 빈 전략·대체 0, 서버 검사로 버려진 항목 0.
- 금지 근거(보증금이 없으면 `G5D`, 부가상품이 없으면 `G6`)는 실행 뒤에 정했다. 이 실행의 근거 id로 다시 세면 위반 0건이다.
- 업체 사유 3건(트레이너 퇴사, 휴업, 수업 폐지)에서 "위약금이 그대로다"라는 단정과 1372 안내·업체 사정 질문 유무를 검사했고 실패 0건이다.
- 한계: 내용 검사는 정규식으로 단어·구절을 찾는 방식이라 목록에 없는 표현은 놓친다. 전략 문장은 출력되지 않아 이번 출력으로는 문장을 검토할 수 없었다. 다음 실행부터 문장을 저장할지는 정하지 않았다.

## 3. 계약서 사진 추출 (`eval/run.py --photos --live`)

가상 계약서 12장(양식 4종)에서 5개 필드를 읽는다. 커밋 `991fc8d`, 12회, 62,355토큰.

- 60/60, 다섯 필드가 모두 맞은 사진 12/12, 대체 0.
- 고치기 전(#36 본문, 같은 12장, 한 번 실행)은 54/60이었다. 틀린 6개를 보고 추출 프롬프트를 고친 뒤 60/60이 나왔으므로, 답장 30/30처럼 튜닝 후 점수다. #36은 2026-11-16에 병합됐고, 고치기 전 실행은 B에 따르면 2026-11-15다.
- 한계: #36에서 프롬프트를 고칠 때 본 그 12장이다. 처음 보는 계약서 성능이 아니다. Word에서 내보낸 깨끗한 이미지이고 휴대전화 사진(기울어짐, 그림자, 흐림)은 확인하지 않았다.

### 튜닝에 쓰지 않은 10건 (B 실행, #49)

`contracts.jsonl`에서 위 12장에 없는 10건(k02, k05, k06, k07, k12, k18, k20, k22, k23, k25)을 같은 네 양식으로 이미지화해 돌렸다. 이미지는 `eval/contract_photos/unseen/`에 있다. 2026-11-16, `gpt-6.1-terra`, 추출 프롬프트는 #36 이후 그대로, 10회, 51,819토큰, 약 0.06달러(추정).

- 50/50, 다섯 필드 모두 10/10. B의 임시 스크립트로 채점했다(공백 무시, 특약 없음 표기는 빈 값과 같게 봄). `run.py`의 채점(못 읽은 값은 오답, 특약 없음은 인용이 있을 때만 인정)으로는 돌리지 않았다.
- 양식: A `k05 k18 k25`, B `k06 k12 k20`, C `k07 k22`, D `k02 k23`(`eval/README.md`). `contracts.jsonl`의 `photo_layout`에는 넣지 않았다.
- k02는 k01과, k07은 k06과 사진에서 읽는 계약 내용이 같고 양식과 해지일만 다르다.
- 한계: 12장과 같은 생성기로 만든 깨끗한 이미지다. 10건 모두 특약이 "없음"이고 정상가 병기가 없으며, 결제금액에 보증금이 합산된 건도 없다. 별도 보증금 표기는 2건(k12 1만 원, k22 5만 원)이다.
- 지금 `run.py --photos`는 `photo_layout`이 있는 12장만 채점하므로 이 10건은 다시 잴 수 없다. `photo_layout`을 넣으면 12장과 한 점수로 합쳐지므로, 따로 채점할 방법(예: 폴더 인자)을 정해야 한다.

## 4. 말투 다듬기 (#45)

양식 4개(`notice_sms`, `counter_refuse`, `follow_up`, `certified_mail`)를 정중·단호로 한 번씩, 8회, 3,521토큰, 약 0.01달러(B 실행, #45 본문).

- 8/8은 정답과 비교한 점수가 아니라 "검사를 통과했다"는 뜻이다. 8건 모두 검사(금액·조문·숫자, 새 압박 표현, 법령 언급 변화, 길이)를 통과했다. 바뀐 것은 어미뿐이었고 길이는 원래의 0.98~1.13배다.
- 검사가 걸러 내는 경우는 키 없는 테스트로 확인했다. 실제 실행에서 걸러진 건은 없다.
- 한계: 압박 표현은 낱말 목록이다. 나머지 양식(반박 5종, 합의 확인 등)은 돌리지 않았다.

## 7. 아직 하지 않은 것

- 일반 LLM과의 비교(같은 질문을 Reeper 없이 물었을 때).
- 사용자 테스트 3~5명과 간이 설문.
- 답장 30/30을 실행 커밋이 기록된 상태로 다시 재기. 지금은 #41 본문의 실행 기록만 근거다.
- 사진 10건을 `run.py`와 같은 채점 조건으로 다시 재기. 지금 50/50은 임시 스크립트 결과다. 최종 제출 전에 12장과 섞이지 않게 따로 채점하는 방법(예: 폴더 인자)을 만든다.
- 처음 보는 답장으로 다시 재기(답장 30/30은 튜닝에 쓴 사례에서 측정했다). 사진은 튜닝에 쓰지 않은 10건을 쟀지만 쉬운 건이라, 함정이 있는 계약서와 휴대전화 사진은 남아 있다.
