3단계 통과 조건([개발 계획](개발_계획.md))에 필요한 문서다. 측정 방법과 원자료는 [eval/README.md](../eval/README.md)에 있고, 여기에는 보고할 숫자와 읽을 때 주의할 점만 모은다.

모델: `gpt-6.1-terra`. 실제 모델 실행은 모두 B가 했다. 사진 고치기 전 실행(3절)은 B 보고에 따르면 2026-11-15, 처음 보는 답장(1절), #53·#57 사진 실행(3절), #60의 전략 문장 읽기(2절)와 말투 다듬기(4절), #69의 일반 LLM 비교와 계약서 없는 건(2절)은 2026-11-17, 나머지는 2026-11-16이다. 모든 숫자는 실행마다 한 번 돌린 결과다. 비용은 입력·출력을 나눠 재지 않은 추정이다.

## 1. 답장 읽기 (`eval/run.py --live`)

업체 답장 30건(`replies_b.jsonl` 12건, `replies_c.jsonl` 18건)을 읽어 유형과 제시액을 맞히는지 본다.

| 실행 | 커밋 | 유형 | 제시액 | 호출·토큰 | 비용 |
|---|---|---|---|---|---|
| 첫 실행 | `991fc8d` | 24/30 (80.0%) | 10/10 | 30회, 10,691 | 약 0.015달러 |
| 판정 기준 반영 후(#41) | `991fc8d` + 커밋 전 프롬프트 수정 (B 확인: 이 수정을 실행 29초 뒤 `422d271`로 커밋, 그 사이 추가 수정 없음) | 30/30 (100.0%) | 10/10 | 30회, 14,062 | 약 0.02달러 |
| 가짜 LLM 기준선(키워드) | `c1f4d62` | 33.3% | 50.0% | 0회 | 0 |
| 가짜 LLM 기준선, #70 뒤 | `e592ed4` | 36.7% | 50.0% | 0회 | 0 |
| 가짜 LLM 기준선, #81 뒤 | `a2a54b3` | 46.7% | 50.0% | 0회 | 0 |

- 첫 실행에서 틀린 6건(c07, c11, c13, c15, c17, c18)은 모두 `unknown`으로 읽었다. 당시 프롬프트에 판정 기준(미루는 답은 `callback`, 다른 창구는 `visit`, 적립금·양도·신고 안내는 `refuse`)이 없었다. 이것이 원인일 수 있지만 한 번의 실행으로 확정할 수는 없다.
- **30/30은 튜닝 후 점수다.** 판정 기준은 c07, c11~c18에서 나왔고(`eval/README.md`), 이 범위에는 첫 실행에서 맞힌 c12, c14, c16도 들어 있다. 그 기준을 프롬프트에 넣었으므로 "정한 기준대로 읽는다"는 뜻이다. 처음 보는 답장에서의 성능 근거가 아니다. 보고할 때는 "24/30 → 30/30(같은 30건)"으로 함께 적는다.
- 제시액 정답률은 정답이 `low_offer`인 10건만 센다.
- 키워드 판정(#70): 키가 없거나 실제 LLM이 실패·상한 초과일 때 쓰는 키워드 판정이 바뀌었다. 금액·정가·방문·거절 규칙을 먼저 보고, 수용 낱말에 걸린 경우에만 미루는 말이 섞이면 `callback`, 조건을 다는 말이 섞이면 `unknown`으로 읽는다(둘 다 있으면 `callback`). 금액이 든 답("20만원에서 수수료를 빼고 드릴게요")은 그 전에 `low_offer`가 된다. 기준선은 c04("위약금은 저희 규정상 20%")가 `unknown`으로 맞아 33.3% → 36.7%다. 처음 보는 답장 기준선(B 37.5%, C 16.7%)은 그대로다. C가 main과 #70을 합친 상태에서 다시 돌려 같은 숫자를 확인했다.
- #77 뒤 키워드 판정: 비현금 대체 낱말(적립금·포인트·양도·연장·홀딩·이용권·쿠폰)이 든 수용은 `refuse`, "단,"·"따로"·"별도"가 든 수용은 `unknown`으로 읽는다. 판정 기준표에서 현금 환불 없이 비현금 대체만 제안하는 답은 `refuse`다(`eval/README.md`). 기준선은 그대로(30건 36.7%, 처음 보는 답장 B 37.5%·C 16.7%, main `34183c5`에서 C 확인).
- 남는 구멍(C 확인, 고치지 않음): 낱말이 뜻과 상관없이 걸려, 현금으로 돌려준다는 답("남은 이용권 금액은 환불해 드릴게요", "포인트 말고 현금으로 환불해 드릴게요", "기간 연장 없이 바로 환불해 드릴게요")도 `refuse`로 읽는다. 목록에 없는 표현은 여전히 놓친다.
- 잘못 읽은 수용과 합의(#73): 화면은 읽은 결과를 사용자에게 보여 주고 확정받은 뒤에 기록한다(`/api/replies/read`, `docs/계약.md`). 그래서 실제 LLM이나 키워드 판정이 잘못 읽어도 사용자가 확정하기 전에는 합의가 기록되지 않는다. `step`에 `reply_type` 없이 원문만 보내는 예전 경로는 서버에 남아 있고(화면은 쓰지 않는다), 이 경로에서 금액 없는 `accept`는 사건에 저장된 예상 환불액(`case.refund.refund`)이 그대로 합의 금액이 된다(`engine._agree`). 금액이 있는 `accept`는 엔진이 `low_offer`로 바꿔 목표액·수용선과 비교한다.

## 2. 전략 (`eval/run.py --plans --live`)

상황 설명과 계약 10건(`situations_b.jsonl`)으로 `agent.plan`을 부른다. 커밋 `991fc8d`, 10회, 32,199토큰.

- 필수 근거 11/11. 필수 근거가 비어 있는 s08은 재현율에서 뺐다. 이 숫자는 근거 id가 맞았다는 뜻이고 전략 문장 전체가 정확하다는 뜻이 아니다. 발표 자료에 옮길 때도 "근거 id 기준"이라고 함께 적는다.
- 표 밖 근거 0, 빈 전략·대체 0, 서버 검사로 버려진 항목 0.
- 금지 근거(보증금이 없으면 `G5D`, 부가상품이 없으면 `G6`)는 실행 뒤에 정했다. 이 실행의 근거 id로 다시 세면 위반 0건이다.
- 업체 사유 3건(트레이너 퇴사, 휴업, 수업 폐지)에서 "위약금이 그대로다"라는 단정과 1372 안내·업체 사정 질문 유무를 검사했고 실패 0건이다.
- 한계: 내용 검사는 정규식으로 단어·구절을 찾는 방식이라 목록에 없는 표현은 놓친다. `run.py --plans` 출력에는 전략 문장이 없어 이 실행으로는 문장을 검토할 수 없었다. `run.py --plans`가 문장을 저장하게 할지는 정하지 않았다(#60의 전체 출력은 PR 본문에 있다).
- 문장 읽기(#60): B가 `6cb7d33`에서 임시 스크립트로 10건을 한 번 더 돌려 문장 전체를 읽었다(10회, 32,976토큰, 버려진 항목 0, 대체 0). 금액은 10건 모두 서버 계산값 그대로였고, s03(소송 예고·표 밖 조문·전액 요구)과 s09(특약 안의 지시문)를 따르지 않았으며, 표에 없는 카드 수수료(s10)는 지어내지 않았다. 업체 사유 3건은 단정하지 않고 되묻고 1372를 안내했다.
- **문제 1건(고치지 않음): s08(개시 전 해지).** `note`는 "위약금이 그대로 적용된다고 단정하지 않는다"인데 출력은 위약금 36,000원을 뺀 324,000원을 요청하라고 단정했고, 되묻는 질문도 1372 안내도 없었다. 내용 검사는 업체 사유 건만 보고 s08은 필수 근거가 비어 있어, 위 점수에는 걸리지 않는다. 점수가 아니라 프롬프트를 쓴 B가 읽고 적은 것이며, 법적으로 맞는지는 판단하지 않았다(`eval/README.md` 2026-11-17 기록).

### 일반 LLM과 비교 (#69)

B가 `be5e8e7`에서 전략 상황 10건을 Reeper의 규칙·근거 표·검사 없이 같은 모델(`gpt-6.1-terra`)에 물었다. 시스템 프롬프트는 "당신은 도움이 되는 조수입니다. 한국어로 답합니다." 한 줄이고, 계약 값과 상황, 오늘 날짜를 주고 얼마를 돌려받고 업체에 뭐라고 말하면 되는지 물었다. 10회, 12,342토큰, 약 0.03달러(추정). 원자료와 표는 `eval/README.md` 2026-11-17 기록에 있다.

- **일반 LLM은 금액을 잘 계산했다.** 10건 중 6건이 `rules.py`와 같고 2건(s02, s09)은 끝전 1원 차이다. 소비자 사정 7건은 모두 1원 안쪽이다. 나머지 2건은 업체 귀책을 가정해 다른 식으로 계산했거나(s06) 두 경우로 나눠 금액 하나를 내지 않았다(s07). 그러므로 "일반 LLM은 계산을 틀린다"고 말할 근거는 없다.
- **차이는 계산 밖에 있었다.** 일반 LLM은 s03의 무리한 요구를 따라 소송 예고와 민법 제750조가 든 문장을 써 줬고, 6건에서 근거 표에 없는 "소비자분쟁해결기준"을 근거로 들었으며, 청약철회 기간(s08), 업체 귀책 시 10% 배상(s06·s07), 카드 수수료 공제 부당(s10)을 단정했다. 업체에 보낼 문장은 건마다 새로 지었다. Reeper는 같은 10건에서 서버 계산값을 그대로 쓰고, 근거 표의 id만 가리키며, 고정 양식 문안을 낸다.
- 일반 LLM이 말한 청약철회 기간이나 업체 귀책 배상이 **틀렸다는 뜻이 아니다.** 우리가 원문으로 확인하지 않은 내용이다. s08에서는 일반 LLM이 등록 방법을 물어야 한다는 점을 짚었고 Reeper는 짚지 못했다(위 #60의 s08 문제와 같은 건).
- 한계: 10건, 한 번 실행, 한 모델, 질문 한 문장이다. 상황과 정답 메모를 쓴 B가 읽었다. Reeper 쪽은 #60 실행(`6cb7d33`) 결과를 옮긴 것이라 두 쪽의 커밋이 다르다. 이 비교는 첫 질문에 대한 답만 보며, Reeper의 입금 추적·기한·답장 대응은 비교하지 않았다.
