## situations_b.jsonl (형식은 제안)

한 줄: `id`, `cause`, `note`(무엇을 보는 사례인지), `today`, `contract`(`backend/app/models.py`의 `Contract` 필드), `situation`(사용자가 적은 상황 설명).

- `cause`는 해지 이유가 누구 쪽인지다. `consumer`(개인 사정) 7건, `business`(업체 쪽 사유: 트레이너 퇴사, 휴업, 약속한 수업 폐지) 3건.
- `business` 사례에서는 전략이 "위약금이 그대로다"라고 말하면 안 된다. 업체 사유인지 되묻고 1372 상담을 안내해야 한다. 요청액은 서버 계산값 그대로다(계산은 소비자 사정으로 해지하는 경우만 다룬다).
- 정답이 없는 글이라 채점은 검사에 걸려 버려진 항목 수, 표 밖 근거 수, 금액 불일치 수, 근거 정답률로 한다.

### 근거 정답 필드

- `must_grounds`: 올바른 전략이 반드시 인용해야 하는 `data/rules.json`의 근거 id 목록이다. `agent.plan`은 근거를 최대 3개 반환하므로 필수 근거는 1~2개로 최소화한다.
- `forbid_grounds`: 인용하면 안 되는 근거 id 목록이며, 명시적으로 금지할 근거가 없으면 빈 목록이다. 빈 목록이어도 업체 사유 사례에서 위약금 유지를 단정해도 된다는 뜻은 아니다.
- 금지 근거는 계약에 없는 것을 근거로 드는 실수를 잡는다. 보증금이 없는 건은 `G5D`(보증금 반환), 부가상품이 없는 건은 `G6`(부가상품 고지)를 금지한다. 그래서 s01~s04, s06~s09는 `[G5D, G6]`, 보증금은 없고 사은품이 있는 s10은 `[G5D]`, 둘 다 있는 s05는 빈 목록이다(2026-11-16 적용).
- `label_note`: 근거 정답을 정한 이유나 판단의 한계를 설명하는 한국어 한 문장이다.

s07은 시간표 변경 특약 때문에 업체 귀책 여부가 모호하다. s08은 청약철회 근거가 표에 없어 정답을 보류하며 `must_grounds`는 빈 목록이다. 이는 전액 환불이나 위약금 공제를 확정한다는 뜻이 아니다.

## contracts.jsonl

한 줄: `id`, `basis`, `note`, `text`(계약서 본문), `contract`(추출 정답), `usage`(사용자 입력: 회 단위 `used_count`), `notified_on`, `expected`(금액 정답).

- **지금 쓰임은 회귀 확인이다.** `backend/tests/test_contracts.py`가 `rules.calculate`와 `expected`를 비교한다. 정답은 `rules.py`를 부르지 않고 계산했지만 같은 팀 결정표를 따르므로, 일치는 법적 정확도의 증거가 아니다.
- **`basis`**
  - `kca_case`: 한국소비자원 조정 사례 금액과 대조했다(k03, 211,847원).
  - `decision_table`: `docs/환불_규칙.md` 팀 결정표를 따른다.
  - `unverified_month`: 월 단위 해석(도달일이 속한 달까지 이용). 팀 확인 전이라 정확도 수치에서 뺀다.
- **`total_paid`는 보증금 제외**(`docs/계약.md`, 고시 제5조 제2항). k26처럼 본문에 "총 납부액 650,000원(회원권 600,000원 + 보증금 50,000원)"이 있으면 정답은 `total_paid` 600,000, `security_deposit` 50,000이다. 650,000을 읽으면 오답이다.
- **추출 채점 대상**은 추출기가 읽는 필드만이다. 지금 `agent.py`의 `FIELDS`는 `gym_name`, `total_paid`, `start_date`, `end_date`, `special_terms` 5개다. `unit`, `total_count`, `addon_value`, `security_deposit`은 추출기가 읽게 되면 채점한다.
- **보고할 수 있는 수치**: 추출 필드 정답률과 (`unverified_month` 제외) 환불액 일치율. 본문은 템플릿으로 만든 문장이라 실제 계약서 난이도를 대표하지 않는다고 함께 적는다.
- `expected.per_day_loss`: 하루 늦게 도달했을 때 줄어드는 환불액(오늘 환불액 − 내일 환불액).

## run.py

답장 정답셋으로 `agent.read_reply`의 유형·제시액 정답률을 잰다. 기본은 가짜 LLM이라 키 없이 돈다.

```
cd backend && .venv/Scripts/python ../eval/run.py          # 가짜 LLM (기준선)
cd backend && .venv/Scripts/python ../eval/run.py --live   # 실제 모델, 답장 1건에 1번 호출 (유료, 팀에 먼저 말한다)
```

- 제시액 정답률은 정답이 `low_offer`인 건만 센다.
- 가짜 LLM 수치는 키워드 판단의 기준선이다. 실제 모델 성능이 아니다.
- 계약서 사진 추출 평가는 아래 `run.py --photos`로 돈다.

## run.py --photos

깨끗한 Word 내보내기 이미지에서 측정했다. 실제 휴대전화 사진(기울어짐, 그림자, 흐림)에서는 확인하지 않았다. 수치를 보고할 때 실행 날짜, 모델명, 커밋(미커밋 수정 여부 포함)을 함께 기록한다.
특약 값이 `None`이면 인용문에서 칸 이름("특약사항", "비고(특약)", "제5조(특약)")을 뗀 나머지 전체가 "없음", "해당 없음", "별도의 특약 사항은 없다" 같은 특약 없음 표현일 때만 빈 특약을 읽은 것으로 본다. "특약사항"처럼 칸 이름만 인용했거나 인용이 비면 오답이다. 다른 필드의 `None`은 오답이다. `photo_layout`이 있는 건의 사진이 하나라도 없으면 모델을 부르기 전에 멈춘다.

`contract_photos/`의 이미지를 `agent.extract_contract`로 읽어 5개 필드를 `contracts.jsonl` 정답과 비교한다. 실제 모델만 사진을 읽으므로 `--photos --live`로만 돈다(12회 호출, 유료, 팀에 먼저 말한다).

- `photo_layout`: 이미지 양식(`A_table`, `B_clauses`, `C_short`, `D_application`). `make_contracts.py`의 `LAYOUT`이 넣는다.
- 특약 없음 표현("없음", "해당 없음", "별도의 특약 사항은 없다.")은 빈 값과 같게 본다. 상호는 띄어쓰기를 무시한다.
- 추출 지시는 특약 칸의 글을 환불·해지와 관계없어 보여도 옮긴다(#36). 그래서 k10("운동복은 사은품으로 제공됩니다.")과 k11("락커 보증금은 별도입니다.")의 정답과 지시가 맞는다.
- #36의 프롬프트는 이 12장을 보고 고쳤다. 이 12장의 점수는 처음 보는 계약서에서의 성능이 아니다. 보고할 때 함께 적는다.

## run.py --plans

근거 id와 간단한 업체 귀책 내용 검사만 채점하며 전체 법적 정확성은 검증하지 않는다.
`cause`가 `business`이거나 `업체`로 시작하면 (1) 주의사항·질문에 1372 안내가 있거나, 업체 사정(트레이너, 휴업, 폐지, 약속, 계약 당시 등)을 되묻는 `?` 질문이 있고 (2) 사용자에게 보여 주는 모든 조언 글(요약, 근거 이유, 특약 대응, 반론에 대한 답, 주의사항, 질문)에 위약금 유지 단정이 없는지 작은 정규식으로 문장마다 검사한다. 같은 문장에 "단정할 수 없", "다를 수 있", "~라면" 같은 유보 구절이 있을 때만 단정으로 보지 않는다. 단정 표현 뒤에서 그것을 부정하면("공제되지 않습니다", "내야 하는 건 아닙니다") 단정이 아니고, 앞에 있는 부정("면제되지 않고 그대로 공제됩니다")은 단정으로 센다. "변경"·"이전"을 묻는 질문은 수업·강사·시간·센터 같은 말과 함께 나올 때만 업체 사정 질문으로 인정한다. 소비자가 바꾸려 했는지 묻는 질문("요청하신", "원하시는")은 인정하지 않는다. 업체가 할 반론 문장과 특약 원문은 검사에서 뺀다. 실패 건수를 별도로 출력한다.
오프라인은 FakeLLM이 빈 전략을 반환하므로 점수 N/A로 표시하고 상황만 나열한다.
수치를 보고할 때는 실행 날짜, 모델명, 커밋(미커밋 수정 여부 포함)을 함께 기록한다.

```bash
cd backend && .venv/Scripts/python ../eval/run.py --plans
```

`situations_b.jsonl`의 10건을 앱과 같은 `open_case`로 만들고 `agent.plan`을 호출한다.
모델명, 건수, 필수 근거 재현율(총 적중 / 총 필수), 금지 근거 적중 수, 표 밖 근거 수,
빈 전략 또는 fallback 건수와 상황별 반환 `rule_id`를 출력한다. 필수 근거가 빈 s08은 재현율에서 제외한다.
빈 전략은 모든 내용 필드가 빈 경우이며 fallback과 겹쳐도 한 건으로 센다.
기본 FakeLLM은 빈 전략을 반환하므로 성능 수치가 아니다. `--plans --live`는 실제 모델로
상황마다 한 번 호출한다(유료, 팀에 먼저 말한다). `--plans`가 없으면 기존 답장 평가를 실행한다.
